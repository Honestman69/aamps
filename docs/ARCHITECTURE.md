# AI 智能体接入多平台管理系统 · 架构设计

> 版本 v0.1 · 2026-10-23
> 三个已定决策：走第三方协议（OneBot 11）、追求拟人而不是问答、纯自用但预留扩展空间。

---

## 1. 设计原则

### 1.1 走第三方协议，所以"接入层"必须是一个可替换的边界

NapCat 提供的是 OneBot 11 协议（WebSocket），**两种接法都已实现**：
**反向**（NapCat 连本服务，默认推荐 —— token 由我们在握手阶段校验，且云端无需开入站端口，见 D019）
与**正向**（本服务连 NapCat）。用哪种由 `BotInstance.adapterMode` 决定，`endpoint` 是地址。这一点决定了：

- 业务代码**不许直接知道** OneBot 的存在，只认内部统一的 `InboundMessage` / `OutboundAction` 结构；
- 未来若切官方 Bot 通道、或 NapCat 挂掉要换 Lagrange / LLONEOneBot，只改一个 Adapter 实现；
- 协议是第三方逆向的，**封号风险是架构性问题，不是运维问题**——所以风控必须写进主链路（见第 7 节）。

### 1.2 拟人不是提示词问题，是有状态的智能体问题

如果链路是 `消息 → Prompt → 回复 → 发送`，模型再强也一定像机器人，原因不在模型，在**没有决策和状态**：

| 机器人感来源 | 人类行为 | 架构对策 |
|---|---|---|
| 秒回 | 有阅读时间，有时不看 | 阅读延迟 + 打字速度模拟 |
| 每条都回 | 大部分消息只看不回 | 发言决策器（注意力模型） |
| 一次回一大段 | 分几条短消息 | 表达层拆条器 |
| 语气恒定 | 有情绪，会累，会不耐烦 | 情绪/精力状态机，持久化演进 |
| 每次都是第一次见你 | 记得你、关系有远近 | 三层记忆 + 关系进度 |
| 只会被动应答 | 会主动想起你说过的事 | 自主反思任务 + 主动消息 |

所以有一个 **mind（表现层）** 模块。但它只回答三个问题：**什么时候说、说几句、说多快**。它不改写模型的思考过程，也不替模型做决策——智能仍然来自模型本身（见 1.4）。

### 1.3 纯自用，但按"未来可能多租户"的方式组织

不做多租户的**功能**，但做多租户的**形状**：

- 每张业务表都有 `tenantId`，默认值 `"default"`；
- 所有配置读取走 `ConfigResolver`（租户 → 实例 → 角色 → 会话 逐层覆盖），加套餐限制只改这一层；
- 密钥、额度、计费都留 `Noop` 实现，不写死"只有一个用户"的假设。

代价大概是**多写 5% 的代码**，收益是后期不用重写。

### 1.4 边界：不做智能体框架，只做调用与包装

这条要提前划死，否则范围会失控。

**不做的：**

- 不自研 Agent 运行时（工具调用、多步 ReAct、任务规划、子智能体编排）
- 不自建 RAG / 向量检索（第一版）
- 不训练、不微调模型
- 不做 Prompt 自动优化

**做的：**

- 托管用户提供的 API Key（DeepSeek、OpenAI、通义、智谱、硅基流动……）
- 把「人设 + 上下文 + 规则」拼成一个请求发出去，拿回文本
- 记录 token 用量与成本，做预算告警
- 在发出前、收到后做管道处理（内容审核、拆条、延迟）

一句话：**智能来自模型和提示词，我们只做调度和包装。** 好处是模型越强，后台的 AI 能力自动跟着变强，我们不用追版本。

同理，用户要"会思考"，正确做法是把主模型指向 `deepseek-reasoner` 这类推理模型，而不是我们在外面套一层思维链编排。

详细设计见 [`MODEL-ACCESS.md`](./MODEL-ACCESS.md)。

### 1.5 部署者是全权限管理员，但看不到任何人的 Key

这条是硬约束，不能因为"自用"就妥协：

- **权限**：部署者 = `superadmin`，系统配置、用户管理、实例与人设、审计日志，全部可管。
- **数据**：任何用户上传的 API Key，只有该用户本人能看到明文。superadmin 能看掩码、能紧急停用，但**不存在读明文的代码路径**。
- **实现方式**：不是加一个 `if` 判断，而是权限枚举里根本没有 `credential.read.plaintext` 这个 action；返回类型里也没有密钥字段；查询在 where 里就带上 owner。三层都堵死。

技术上靠**信封加密**：每把 Key 用用户私有的 DEK 加密，DEK 由用户密码派生的 KEK 包裹，服务端不保存任何能解开它的材料。代价是服务重启后需要用户重新解锁一次——这个取舍是刻意的，不接受"用服务端主密钥再包一层"的便利方案，因为那等于把部署者变成可解密者。

完整威胁模型、参数、落地检查清单见 [`SECURITY.md`](./SECURITY.md)。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | Node.js 22 + TypeScript | OneBot 生态、NapCat 自身都是 TS，心智与类型一致 |
| 后端框架 | NestJS（Fastify 适配器） | Module + DI 天然对应"可替换实现"，是扩展预留最省力的框架 |
| ORM | Prisma | 一份 schema 同时产出类型与迁移；SQLite → PostgreSQL 改一行 datasource |
| 数据库 | SQLite（WAL 模式） | 自用单机足够，零运维。消息日志量大后再迁 PG |
| 队列 | 进程内串行（`PipelineService.sessionQueue`，按会话分片） | 现在**没有队列系统**：消息按会话串行就够，单机不需要 Redis。真要做异步任务（反思、清理）再引入 |
| 定时任务 | 依赖已装（`@nestjs/schedule`），**尚未使用** | 反思、主动消息、清理三类 cron 属 M5/M6；现在状态靠"读时衰减"，不需要定时器 |
| 前端 | Vue 3 + Vite + Element Plus + Pinia | 中后台组件齐、开发快 |
| 部署 | 当前：单进程 `node dist/src/main.js`（同源托管前端）；计划：Docker Compose（app + napcat） | 一台小服务器即可；**容器化还没做** |
| 日志 | pino + 结构化字段 | 单条消息可全链路追踪 |

**为什么不用 Python**：OneBot 生态里 Python 的 NoneBot 很成熟，但心智引擎要做大量并发定时器（打字延迟、状态衰减、心跳），TS 的 event loop 模型更省心，且前后端同语言省一套类型定义。

## 3. 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  Admin UI (Vue3)                                         │
└───────────────────────┬──────────────────────────────────┘
                        │ REST / SSE
┌───────────────────────┴──────────────────────────────────┐
│  Control Plane  配置面                                     │
│  persona · rules · credential · instance · compliance     │
│  只负责"存配置、校验、发版本"，不参与消息处理                    │
└───────────────────────┬──────────────────────────────────┘
                        │ ConfigResolver（逐层覆盖 + 缓存）
┌───────────────────────┴──────────────────────────────────┐
│  Data Plane  数据面（消息主链路）                             │
│                                                          │
│  Adapter ──▶ Pipeline ──▶ Mind ──▶ LLM ──▶ Pipeline ──▶ Adapter │
│  (OneBot)    入站管道     表现层    Provider   出站管道            │
│                                                          │
│  旁路：Memory（记忆）  ·  Rules（规则）  ·  Compliance（合规）    │
│  中枢：ModelGateway（密钥托管 / 路由 / 重试 / 计量）              │
└──────────────────────────────────────────────────────────┘
                        │
┌───────────────────────┴──────────────────────────────────┐
│  Workers  后台任务：反思 / 主动消息 / 状态衰减 / 清理 / 风控巡检    │
└──────────────────────────────────────────────────────────┘
```

**配置面与数据面分离**是关键：改人设不该重启机器人，机器人掉线不该影响后台编辑。两者通过 `ConfigResolver` 的缓存 + 版本号失效连接。

## 5. 消息处理管道

**已落地**（D040 拆出 13 个；M5 加 `load-memory` / `load-self` / `write-memory`；
M6 加 `throttle` 与两条 `guard-*`，共 19 个）：
pipe 在 `src/modules/pipeline/pipes/`，顺序写在 `pipes/index.ts` 一张平铺的清单里。
加功能 = 新建一个 pipe 文件 + 在清单里插一行，不改编排。

```ts
interface Pipe {
  readonly name: string;
  readonly requires: readonly (keyof PipelineContext)[];  // 要读的字段
  readonly provides: readonly (keyof PipelineContext)[];  // 写完的字段
  run(ctx: PipelineContext): Promise<void | Drop>;        // Drop = 到此为止
}
```

`requires` / `provides` 不是装饰：`assertPipeGraph` 在**服务启动时**校验
"用到的字段必须被前序 pipe 提供、同一字段不许两个 pipe 都写、名字不许重复"。
把 `attention` 挪到 `generate` 后面，启动就报错，而不是等线上某条消息返回 `undefined`。

### 入站链（实际顺序 = `pipes/index.ts`）

| # | Pipe | 职责 | 结束时 |
|---|---|---|---|
| ① | `persist-inbound` | 取处理时刻、upsert 会话、入站消息落库 | 抛错 → 兜底 |
| ② | `load-context` | owner + 人设 + 配置（含会话开关） | 实例没了 → DROP |
| ③ | `governance` | 人工接管 / 会话静默 / 夜间群聊 → 只入库 | DROP（不写状态） |
| ④ | `guard-input` | owner 配的入站约束词（D051）：命中就不接 | DROP（标 `blocked`） |
| ⑤ | `load-mind` | 状态衰减到 now、读关系 | 读失败 → 用默认值 |
| ⑥ | `load-window` | 取窗口切片并 `buildWindow`（D031） | 空窗口 → DROP |
| ⑦ | `attention` | **判断要不要回**（详见 6.2） | 不回 → 写状态/关系后 DROP |
| ⑧ | `collect-media` | 入站图片 → 多模态段、素材清单（D033/D034） | 失败只丢这一张 |
| ⑨ | `load-memory` | 读回记忆：这个人的事实 + 本会话最近摘要（D045） | 读失败 → 空记忆 |
| ⑩ | `load-self` | 读回"现在的你"：自述 + 由特质推出的几句（D046） | 读失败 → 空自述 |
| ⑪ | `assemble-prompt` | 拼 system（D020：红线 → 种子 → 现在的你 → 印象 → 情境 → 语气）+ 消息数组 | — |
| ⑫ | `think` | A 阶段内心独白（D036），产出导演指令 | 失败/关闭 → 退化为无独白 |
| ⑬ | `generate` | B 阶段生成；带图时指定视觉模型且不参与预算降级 | 抛错 → 兜底话术 |
| ⑭ | `guard-output` | owner 配的出站约束词（D051）：命中就不发 | DROP（仍落库并标 `blocked`） |
| ⑮ | `decide-quote` | 引用决策（D030） | — |
| ⑯ | `throttle` | 会话/日上限、连续冷却、复读（D049） | 超限 DROP；连续发言等冷却 |
| ⑰ | `deliver` | 媒体意图 → TTS → 拆条/延迟/回 @ → 发送 + 落库（D033/D035） | 语音失败 → 降级为文字 |
| ⑱ | `persist-interaction` | 花精力、`emotion_shift` 推动 mood、长亲密度 | 吞异常 |
| ⑲ | `write-memory` | 攒够条数就反思：摘要 + 事实写库（D045），顺带人格演化（D046） | **绝不抛**（抛了会多一条兜底话术） |

**两种"不回"必须区分**：`DROP` 是"判定不该回"（安静结束），`throw` 是故障
（交给 `PipelineService.handleFailure` 按 D028 分槽位说兜底话术，可能静默）。
混成一种，要么欠费时每句都回"我有点累"，要么模型挂了却一声不吭。

**为什么 attention 在 generate 之前**：这是省钱又拟人的关键。自用场景下 60%~80% 的群消息不该回，提前判掉既省 token 又避免"有问必答"。

### 设计里还有、实现里还没有的三个 pipe

`normalize`（协议事件 → `InboundMessage`，现由适配器包承担）、
`dedupe`（事件去重，现依赖平台的 message id 唯一性）、
`moderate`（输出审核，M6 的合规一起做）。
写在这里是为了**别把"架构图画过"当成"已经做了"**。

### 出站链

出站目前是 `deliver` 一步完成（`express` + `send` + `persist` 合体）：
拆条/延迟/回 @ 与发送、落库是同一件事的三段，分开反而要在两个 pipe 之间传半成品。
等 M6 加入发送节流与合规审核时，再按"节流 → 审核 → 发送"拆成三步。
### 多模态的接缝（D033）

多模态**不是新管道**，只是现有三段各加一次转译：

| 位置 | 做什么 | 失败怎么办 |
|---|---|---|
| `context` 之后 / `generate` 之前 | 入站 `image` 段 → 下载 → base64 data URL → 拼成 `content: [text, image_url]`（只挂当前这条，历史图不重发） | 这张图丢掉，正文留「[图片]」，不影响说话 |
| `generate` 的模型选择 | 带图时指定 `modelVision`，**不参与预算降级** | 没配 `modelVision` 就根本不下载图片 |
| `express` 之前 | 解析模型输出的 `[img]url[/img]` / `[voice]text[/voice]` → 校验 URL → TTS 合成 → 拆成 1~2 条出站 | 校验不过就丢标记；TTS 失败就把那句话当文字说 |

**媒体选择归模型、形态归代码**：模型只说"我想发这张图/这句话用语音"，引用、拆条、延迟、兜底话术
仍然由 `src/` 决定（D030 / 硬性规则 11）。这条边界见 `DECISIONS.md` D033。

**素材库（D034）是这条边界的延续**：`[save]名字[/save]` / `[use]名字[/use]` 里的"名字"是模型唯一的入口，
它不能给 URL。库里存的每张图都至少被真实抓取过一次（`assets/<sha256>.<ext>`），
所以"发图"这个动作对外只有两种来源：**公网白名单 URL** 或 **我们自己落盘的文件**。

**管理面（M4，D039）**：`GET /api/instances/:id/assets`、`DELETE .../assets/:assetId`、
`GET .../assets/:assetId/file`。三个动作对应三件事：**看见它存了什么**（隐私）、
**删掉不想留的**（软删，名字继续占位）、**给缩略图供字节**（同源 + 会话 cookie）。
刻意没有改名、上传、批量删 —— 理由见 D039。

### 记忆的接缝（D045）

记忆**也不是新管道**，而是在两端各插一个 pipe：

| 位置 | 做什么 | 失败怎么办 |
|---|---|---|
| `attention` 之后 / `assemble-prompt` 之前（`load-memory`） | 读回：这个人的语义事实（按 `importance`）+ 本会话最近的情节摘要 → 拼进 system 的「印象」段 | 读不到就是"这次不记得"，对话照常 |
| `deliver` 之后（`write-memory`） | 攒够 `reflectEvery`（默认 30）条就调一次 `purpose: 'reflection'`（走 `modelCheap`）→ 摘要 + 事实写 `MemoryItem` | **绝不抛**：抛了会被当成故障，对方会在正常回复之外再收到一句兜底话术 |

两层就够，不做三层：**工作记忆 = 会话窗口本身**（原文已在 `Message` 表，按 D031 裁剪），
再存一份进记忆表只会得到两套不同步的真相。`SelfState`（演化层）与自我叙事仍是设计里的 M5-2/M5-3。

## 6. 心智引擎（mind）

### 6.1 状态模型（持久化在 `agent_state` 表）

| 状态 | 范围 | 变化 | 影响 |
|---|---|---|---|
| `mood` 情绪 | -1 ~ 1（效价） | 被对话内容推动，每小时向基线回归 8% | 影响用词温度、语气词密度 |
| `energy` 精力 | 0 ~ 1 | 按作息曲线波动（深夜低、午休低谷） | 低时回复更短、回复率下降 |
| `affinity` 亲密度 | 0 ~ 100（每个用户独立） | 按互动深度/频次累积，长期不说话缓慢衰减 | 决定称呼、可聊话题深度、主动消息频率 |
| `busy` 忙碌 | 布尔 + 截止时间 | 主动消息或手动设置 | 忙碌时回复延迟 ×3 |
| `mute` 静默 | 截止时间 | 群管理触发、风控触发 | 完全不出声 |

### 6.2 发言决策（attention）

不做二分类，做一个连续唤醒度：

```
wake = base
     + 0.45 * isMentioned          // @ 或被叫名字
     + 0.30 * topicMatch(兴趣标签)   // 与角色兴趣设定相关
     + 0.20 * 追问上一轮的对方
     + 0.15 * 群内当前活跃度
     - 0.30 * (1 - energy)
     - 0.20 * isMuted
wake *= decay(Δt)                  // 随时间指数衰减
decide = wake > threshold(busy ? 0.75 : 0.55)
```

阈值、权重全部放在人设配置里可调（不同性格的角色，阈值不同：话痨 0.35、高冷 0.8）。

私聊与群聊分开：私聊默认几乎必回（阈值 0.05），群聊才是决策重点。

> **实现现状（M3-1，见 D032）**：`src/modules/mind/state/`（mood/energy 衰减 + 亲密度）与
> `src/modules/mind/attention/`（阈值与权重来自 `Persona.behaviorJson.attention`）已接入 Pipeline，
> 判定发生在**调模型之前**。与上式的差异只有两处：`busy` 只抬高群聊阈值（私聊的忙碌是延迟不是失联），
> 以及**群里被 @ 必回**（硬规则，不参与阈值比较）。`reflection/`（内心独白，D036）与
> `expression/`（拆条与打字延迟，D035）也已落地 —— 也就是说 6.2 / 6.3 / 6.4 三节现在都是"实现现状"。

### 6.3 双阶段生成

单次调用容易"工整"，两段式才自然：

**A. 内心独白（不进历史）**
prompt 要求模型先输出一段结构化思考：

```json
{
  "want_to_reply": 0.82,
  "emotion_shift": -0.15,
  "intent": "对方在抱怨加班，想被安慰",
  "key_points": ["共情", "不问细节", "提一句上次说的项目"],
  "tone": "有点心疼，别太用力",
  "length_hint": "短，1-2句"
}
```

**B. 外显生成**
把上面的思考作为"导演指令"注入第二次调用，产出真正发出的文本。这样能出现"想怼但忍住了""被别的话题带跑"这类真实感。

成本控制：`length_hint` 短时 A 阶段可以用小模型/低 temperature，B 阶段才用主力模型。

> **实现现状（M3-4，见 D036）**：`src/modules/mind/reflection/` 已落地。A 阶段走
> `gateway.chat({ purpose: 'think' })`（`modelCheap` 记账），B 阶段把独白翻译成"导演指令"拼进 system。
> 与上式的差异：`want_to_reply` **不参与"要不要回"的判断**（那只影响语气），
> 因为 attention 已经决定过；思考只落 `Message.thinkJson`，**绝不回灌历史**。
> 失败（解析不出 JSON / 调用报错）→ 退化为单阶段，不影响回话。

### 6.4 表达层（expression）

人类特征是可以工程化的：

- **拆条**：按句号/换行切分，合并成 1~3 条，单条上限 40 字（超出必拆）
- **打字延迟**：首条前 `阅读时间 = 0.8s + 字数 * 0.05s`（随机 ±30%），后续每条 `字数 / 4.5 秒`；忙碌时 ×3，深夜 ×1.6
- **偶发行为**（概率可配，默认低）：补发错别字修正、撤回、追加一个表情、语音条
- **@与引用**：群里被 @ 时先 @ 回，被引用时先提一句引用内容
- **不连发同一句式**：检查最近 5 条，重复开头换说法

所有随机都过 `seededRand(conversationId + timestamp)`，方便复现 bug。

> **实现现状（M3-3，见 D035）**：`src/modules/mind/expression/` 已落地拆条、延迟、回 @，
> 文本/图片/语音分三条发；同一会话在 `PipelineService` 里串行，后一条等前一条说完。
> 与上式的差异：`maxCharsPerSegment` 只作目标（**绝不截断**）、延迟有 12s 总上限（按比例压缩）、
> 已用引用时不再 @。**未做**：偶发行为（错别字/撤回/追加表情）、"不连发同一句式"（属模型职责）、
> 连发冷却（归 M6 风控）。

### 6.5 自主性（proactive）

`proactive.worker` 定期扫描，满足条件才动作。**默认关闭**（`BotInstance.proactiveEnabled`），
主动消息是封号高危行为，也是一个会打扰人的行为 —— 开不开是人的决定。

**已落地（M5-3，D047）**：每 10 分钟扫一次，判据是纯函数 `decideProactive`，五道确定性闸门：

| 闸 | 值 |
|---|---|
| 夜间静默 | 23:00–08:00 不发 |
| 亲密度 | ≥ 40 |
| 久未联系 | ≥ 48 小时 |
| 同一人冷却 | 72 小时（比原设计的"每天 1 次"更保守） |
| 实例配额 | 每天 ≤ 3 条 |

生成用主模型（人设 + 记忆 + 演化自述 + 心智状态），**一条、不拆条、不带媒体**；
出站走 `InstanceService.sendOutbound`（与正常回复同一条路），先发后落库并标 `proactive`。

**还没做**：另外两个触发条件 —— （1）未完结话题（"'明天'指的是哪天"要语义提取）、
（2）记忆里的纪念日。两者判断错的代价是凭空编一件事去开场，比沉默糟得多，留给之后的语义能力。

### 6.6 人格的四层与自我演化（D020）

人格不能寄生在上下文窗口或进程内存里，否则重启/爆窗口就等于"重新出生"。所以分四层：

| 层 | 载体 | 谁能改 | 重启后 |
|---|---|---|---|
| 不可演化 | **代码常量**（`rules/red-lines.ts`，D051 修正了 D020 的"独立表"） | 谁都改不了（含 superadmin） | 不变 |
| 种子 | `Persona`（挂在 `BotInstance`，version + archivedAt） | owner 编辑（生成新版本） | 不变 |
| **演化** | `SelfState`（挂在 `BotInstance`，traits + 自述） | **只有反思任务**，过代码闸门 | 从库里恢复 |
| 瞬态 | `AgentState`（mood / energy，挂实例） | 每轮对话 + 衰减 | 从基线重新开始 |

作用域提醒（D023）：这一整套是**每个社交平台账号一份**。同一用户换平台 = 重新生成种子、从零演化；
换模型 Provider **不触发任何人格/记忆变化**——`Persona` / `SelfState` / `MemoryItem` 里没有 provider 字段。

演化循环（默认每日一次，重要事件可加一次即时反思，用 `modelCheap` 记账 `purpose=reflection`）：

```
对话与事件 → 沉淀记忆（含冲突/好感） → 反思（结构化输出）
   → 代码闸门（限幅 ±0.03 · clamp · 记忆引用校验 · 拒改红线 · 落快照）
   → 写回 SelfState（version + 1，可回滚）
```

**代码闸门是这段设计的关键**：模型不直接写库。它只能提交"增量提案"，由代码决定是否接受。
理由有三条：防编造经历（必须引用真实 memoryIds）、防性格跳变（限幅 + 单日累计上限）、防无法回溯（版本快照）。

prompt 组装顺序固定：

```
红线（只读）→ 出生设定（"你出生时…"）→ 现在的你（SelfState 自述）
→ 对这个人的印象（关系 + 语义记忆）→ 情境（时间/平台能力/最近对话）→ 语气提示
```

种子用**过去时叙述**（"你出生时…"），不用命令句（"你必须…"）。后者会让模型背设定，前者才会延续人格。

上下文满了不靠"扩大窗口"，靠分层：工作记忆（最近 N 轮原文）→ 情节摘要 → 语义记忆 → 自我叙事。
原文留在 `Message` 表可检索，只是不进 prompt，所以"忘了"是可逆的。

> **实现现状**：
> - 「对这个人的印象」里的**记忆段**已落地（M5-1，D045，见 5 节「记忆的接缝」）；
> - **演化层**已落地（M5-2，D046）：`SelfState` 四维特质 + 第一人称自述 + 版本快照，
>   闸门写在 `persona/self/evolution.ts`（纯函数），回滚走「追加新版本」而不是删历史；
> - 「自我叙事」（把多段自述压成 ≤600 token 的一段）还没做 —— 现在直接把最近一版自述整段放进 prompt，
>   自述超过 1200 字会被闸门拒收，所以暂时不需要压缩。

## 7. 风控与稳定性（第三方协议专属）

第三方协议最大的风险不是代码 bug，是账号被封。这部分必须进主链路，不能当运维补丁。

### 7.1 行为拟人（发出去的所有动作都要过）

| 维度 | 默认值 | 现状（M6-2，D049） |
|---|---|---|
| 单条消息间隔 | 1.5s ~ 6s 随机 | ✅ 已落地（D035，表达层） |
| 单群每小时上限 | 40 条 | ✅ `throttle` pipe 拒发 |
| 单日总发送 | 800 条 | ✅ 同上，可被实例的 `dailyMsgCap` 覆盖（`0` = 不限） |
| 连续发送上限 | 5 条 | ✅ 之后等 30 秒冷却再发（不是不发） |
| 夜间静默 | 00:30 - 07:30 | ✅ 治理层 DROP；**只作用于群聊**，被 @ 放行，`nightQuiet` 可配 `off` |
| 相似内容检测 | 24h 内重复 > 3 次拦截 | ✅ 归一化（去标点/emoji）后比较，少于 4 字不参与 |

超限一律是「这次不说」而不是「排队补发」—— 半小时后补一句"哈哈"比沉默更像故障。
节流读不到数据时**放行**：数不清就让它说话，别因为一次数据库抖动让它失语。

### 7.1.1 两道闸的分工

| 闸 | 在哪 | 管什么 | 超限时 |
|---|---|---|---|
| 节流（D049） | `11a-throttle` pipe | 发得**太频繁** | 这次不说 / 等 30 秒 |
| 风控（D048） | `risk.worker` → `silentUntil` → `03-governance` | 平台已经**开始拦** | 冷却 / 只收不发 / 停实例 |

顺序很重要：节流在**生成之后**（要拿正文判复读），风控在**读消息之后**（要连模型调用都省掉）。

### 7.2 绝对禁止清单（代码层硬约束，不可配置开启）

- 主动加好友、主动拉群、批量 @全体
- 转发/群发同一内容到多个会话
- 修改群公告、踢人、禁言等管理操作（除非人工确认）
- 高频重连（重连退避指数增长，10 次后停止并告警）

### 7.3 风控信号与自动降级

监听 Adapter 返回码与连接事件：

```
发送失败(风控码) → 连续 1 次：冷却 10 分钟
                 → 连续 2 次：降级为 read-only（只收不发），告警
                 → 连续 3 次：停止实例，人工介入
登录态异常/频繁掉线 → 记录指纹，通知人工
```

`risk.worker` 每 5 分钟巡检一次，输出"实例健康分"（0-100）到看板。
**看板已落地（M6-3，D050）**：后台「健康与事件」页（`/instances/:id/health`）——
上半是实时分数与处置（`GET /risk`，实时算不落库），下半是 `InstanceEvent` 列表（`GET /events`）。
页面**零操作**：不给"解除静默/重置分数"，要看就看，要停就去实例页停用。

**已落地（M6-1，D048）**：信号落 `InstanceEvent`，巡检算分并执行阶梯，静默由治理 pipe 执行。

| 连续被拦 | 动作 | 落到哪一列 |
|---|---|---|
| 1 次 | 冷却 10 分钟 | `silentUntil = now + 10min` |
| 2 次 | 只收不发 6 小时 | `silentUntil = now + 6h`、`status = risk` |
| ≥3 次 | 停实例等人工介入 | `enabled = false`、`status = banned`、断开连接 |

分数（0-100）与阶梯**分开算**：分数给人看（趋势、理由），阶梯给机器执行（只看连续拦截次数）。
静默期间治理 pipe 直接 DROP —— **连兜底话术都不发**，那也是一次发送。

**还没做**：相似内容检测、单群/单日上限、夜间静默的执行、重连退避（M6-2）；看板页面（M6-3）。

### 7.4 数据安全

`AppSecret`、LLM Key、NapCat Token 一律用**所属用户的 DEK** 加密落库（不是全局主密钥），DEK 由用户密码派生，服务端不留解密材料。部署者即使拿到服务器与数据库也解不开。日志里所有密钥、手机号、完整 QQ 号做掩码。

详见 [`SECURITY.md`](./SECURITY.md)。

## 8. 记忆系统

三层，成本递增，按需召回：

| 层 | 存储 | 写入时机 | 读取 |
|---|---|---|---|
| 工作记忆 | 最近 20 轮原文 | 实时 | 全量注入 |
| 情景记忆 | 每日对话摘要 | `reflection.worker` 凌晨跑 | 按时间/话题检索 top 3 |
| 语义记忆 | 用户画像事实（名字、工作、喜好、纪念日、关系事件） | 反思时抽取，去重合并 | 按用户全量注入（量小） |

检索先用 SQLite FTS5 + 关键词加权，够用；量大了换 pgvector，`IMemoryStore` 接口不变。

记忆必须可编辑、可删除（界面里能看"它记得我什么"，这是自用工具的乐趣，也是合规要求）。

## 9. 数据模型

见 `prisma/schema.prisma`。核心关系：

```
Tenant
  ├─ User (1..n)              superadmin / user
  │    ├─ Credential (1..n)   用本人的 DEK 加密，跨用户不可见（Provider 的 Key 池）
  │    └─ BotInstance (1..n)  ★ 一个社交平台账号 = 一段人格（D023）
  │         ├─ Persona (1..n)      种子人设（只读、多版本、可归档）
  │         ├─ SelfState (1)       演化层：traits + 自述（只有反思能写）
  │         ├─ AgentState (1)      情绪/精力（瞬态）
  │         ├─ Relationship (n)    按 [instanceId, peerId] 唯一
  │         ├─ MemoryItem (n)      记忆
  │         └─ Session (1..n)      私聊/群聊会话
  │              └─ Message (n)
  └─ AuditLog (n)             只增不改，哈希链

归属判定：**人格与记忆挂 `BotInstance`**；Provider 只是执行器，不落在人格表的任何字段里。
QQ 号与抖音号是**两份独立人格**，各自演化、互不可见（跨平台合并属另一个项目）。
```

## 10. 扩展预留清单

从"自用"到"多租户 SaaS"，需要改什么、不需要改什么：

| 预留点 | 现状（自用） | 后期改造 | 是否要重写 |
|---|---|---|---|
| 租户 | `tenantId = "default"` 常量注入 | 从 JWT 解析 | 否 |
| 权限 | `superadmin` / `user` 两级，接口已预留 | 增加角色与细粒度授权 | 否 |
| 配置覆盖 | `ConfigResolver` 已实现四级 | 增加套餐限制层 | 否 |
| 接入层 | 只有 OneBot Adapter | 新增 Official Adapter | 否 |
| 模型层 | Credential 已按 owner 隔离、每人独立 DEK | 需要时加跨用户授权 | 否 |
| 队列 | 内存队列 | 换 BullMQ（接口已对齐） | 否 |
| 数据库 | SQLite | 换 PG（Prisma 改 datasource） | 否 |
| 计费 | `NoopBilling` | 实现真实扣费 | 否 |
| 登录 | 单管理员账密 | 加用户表 + OAuth | 是（但只动 admin 模块） |
| 限流 | 单机令牌桶 | 换 Redis 分布式 | 是（只动 rateLimit 实现） |

结论：**9 个扩展点里 7 个不用重写**，只要一开始把接口定对。

### 10.1 新增一个平台 = 新建一个独立包

平台适配器**不在主服务里**，而是独立包（见 D013）。主服务只依赖契约包和各 adapter 包。

**新增平台（以抖音为例）的完整步骤：**

| # | 做什么 | 在哪 |
|---|---|---|
| 1 | 建包 | `packages/adapter-douyin/`（package.json + tsconfig + src） |
| 2 | 写清单 | `src/manifest.ts`：platform / protocol / capabilities / configFields / metrics |
| 3 | 写实现 | `src/index.ts`：`defineAdapter({ manifest, create })` + `IAdapter` 实现 |
| 4 | 注册依赖 | 根 `package.json` 的 dependencies 加 `"@newjob/adapter-douyin": "workspace:*"` |
| 5 | 注册工厂 | 主服务 `modules/adapter/registry.ts` 加一行 |

**之后不需要改任何东西**：前端根据 `manifest.configFields` 自动渲染配置表单，看板根据 `manifest.metrics` 自动出现指标，主服务根据 `protocol` 自动路由。

### 清单驱动到哪一步（D041）

"自动渲染表单"曾经只做了一半：字段渲染了，但**值怎么落到实例上**没人说。现在由清单自己说：

| 声明 | 作用 |
|---|---|
| `ConfigField.mapsTo` | 这个字段的值写进实例的 `accountId` / `adapterMode` / `endpoint` / `accessToken` |
| `ConfigField.requiredWhen` | 条件必填（如"反向模式必须有 token"），前端星号与后端校验同源 |

```
前端：manifest.configFields → 渲染表单 → POST adapterConfig:{字段key: 值}（不翻译）
主服务：assertAdapterManifest（注册时）→ translateAdapterConfig（按 mapsTo 翻成实例列）
```

三条纪律（写在 `src/modules/adapter/manifest-config.ts` 的注释里）：
**字段必须能落到槽位**（否则用户填了也没用）、**清单在注册时校验**（开发者错误让服务起不来）、
**`adapterConfig` 与平铺字段互斥**（同一件事不许有两个来源）。

**主服务里禁止出现的**：`import ... from '@newjob/adapter-douyin'` 之外的任何平台细节；`if (platform === 'douyin')`。

**依赖方向是单向的：**

```
主服务 (src/)  ──依赖──▶  @newjob/adapter-xx  ──依赖──▶  @newjob/contracts
     │                                                        ▲
     └──────────────────────依赖─────────────────────────────┘
```

适配器**永远不依赖主服务**。这条由包结构保证，不靠自觉。

**平台差异仍然是"能力"而不是"分支"：**

| 层 | 与平台相关？ | 说明 |
|---|---|---|
| `@newjob/contracts` | 部分 | 只有 `Platform` 与 `SessionKind` 两个类型 |
| `@newjob/adapter-*` | 是 | 唯一需要写新代码的地方 |
| 主服务 pipeline | 否 | 读 `capabilities` 决定行为 |
| mind / memory / persona / rules / model | 否 | 完全不感知平台 |
| compliance | 否 | 审核强度由 `capabilities.publicReply` 驱动 |
| 前端 | 否 | 表单由 `manifest.configFields` + `mapsTo` 生成（D041） |

真正需要注意的不是代码，而是**语义**：

| | QQ 群 | 抖音评论 | B站弹幕 |
|---|---|---|---|
| 回复可见 | 群内 | **全网公开** | 视频下公开 |
| 主动发起 | 可以 | 需用户先私信（48h 窗口） | 不可以 |
| 单条字数 | 4500 | 1000 | 200 |
| 风控后果 | 账号封禁 | 内容下架 + 限流 | 混合 |
| 消息之外的事件 | 少 | 礼物、进场 | 上舰、醒目留言 |

`publicReply` 这一位是架构级的：QQ 私聊说错话只有一个人看到，B站评论区说错话所有人都看到。所以内容审核策略、AI 标识的强制程度、兜底话术的保守程度，都必须跟着它变。

### 4.1 后台托管与前端边界（D038）

前端是 `web/`（独立 workspace 成员），构建产物 `web/dist` 由**主服务同源托管**
（`src/common/http/serve-admin.ts`）。三条边界：

| 规则 | 原因 |
|---|---|
| 开发期用 Vite 代理 `/api`，生产期同源 | 不为开发方便放宽 `SameSite` 与 CORS（D005） |
| `/api/*` 的 404 永不回落 `index.html` | 否则前端拿到 HTML，报 `Unexpected token '<'` |
| 前端不提供"编辑原始 JSON"入口 | 写路径必须能校验（D037 的延伸） |

**类型不共享**：`web/src/api/types.ts` 手抄服务端 DTO。共享要把两端编译目标对齐，
还会把 zod 打进前端包；手抄的代价只是"改接口记得改两处"。

**M0 必须排在第一位**，不是因为它最紧急，而是因为密钥的存储方式会渗透到每一个 Repository 签名和 DTO 类型。等 M2 写完再补，等于全量返工。

M1~M3 是价值核心，M4 之后是体验完善。建议 M1 到 M2 用一周内跑通，先让它在群里活着，再谈拟人。
