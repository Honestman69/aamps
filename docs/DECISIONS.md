## D001 接入走第三方协议（OneBot 11）

**日期**：2026-10-23
**决策**：通过 NapCat 提供的 OneBot 11 协议接入，不使用 QQ 官方 Bot 开放平台。

**理由**：
- 需求是"机器人在 QQ 里和正常用户拥有一样的完整功能"（进群、主动消息、完整消息类型）。
- 官方平台明确限制：接入 AIGC 的机器人只允许在沙箱环境的单聊使用，不支持群聊与频道，且暂不支持发布上架。
- 官方单主体最多 5 个 Bot，且需要实名与资质。

**代价**：封号风险。这是架构问题，由 D008 承接。

**违反后果**：如果为了"合规省事"改走官方通道，产品会直接失去核心能力（进群对话）。

## D002 不构建智能体框架

**日期**：2026-10-23
**决策**：不自研 Agent 运行时、工具调用、多步 ReAct、RAG 引擎、模型训练。系统只做四件事：托管密钥、拼装请求、调用、计量。

**理由**：
- 用户明确要求："我们自己不需要构建智能体。"
- 智能来自模型和提示词。模型升级，系统能力自动跟着升级，不需要跟着改代码。
- 自研 agent 框架会引入巨大的维护成本，最终变成一个半成品 LangChain。

**具体禁止**：引入 LangChain / LlamaIndex / Dify / 任何工作流编排引擎；实现"工具调用"循环；内置向量数据库。

**违反后果**：项目范围失控，从"一个后台"膨胀成"一个平台"，且核心的拟人体验没有因此变好。

## D003 API Key 用「每用户独立 DEK」信封加密

**日期**：2026-10-23
**决策**：每条 API Key 用该用户私有的 DEK（32B 随机）加密；DEK 由用户密码经 Argon2id 派生的 KEK 包裹后存库；服务端不保存任何能解开 DEK 的材料。

**理由**：
- 硬需求："用户上传的 Key 只对他自己展示，**哪怕是部署者也不行**。"
- 如果用全局主密钥，部署者必然持有它，那么"只有本人可见"就只是一句代码里的 `if`，不是安全保证。

**明确否决的替代方案**：

| 方案 | 否决原因 |
|---|---|
| 全局主密钥 + 环境变量 | 部署者持有环境变量即可解开全部 Key |
| DEK 用服务端 KEK 再包一层后存库 | 换汤不换药，部署者仍可解密 |
| DEK 明文存库 | 等于不加密 |
| 只做前端隐藏 | 抓包即得，毫无意义 |

**违反后果**：核心需求直接失效，且这是那种"看起来能用、实际上随时能被绕过"的假安全，比不做更危险。

## D004 改密码与重置密码是两条独立路径

**日期**：2026-10-23
**决策**：
- 本人改密码 → 用旧密码解出 DEK → 用新 KEK 重新包裹 → **Key 完全保留**（单事务）
- 管理员重置他人密码 → **销毁 wrappedDek**，该用户全部 Key 报废
- 忘记密码 → 按重置处理（无法证明身份）

**理由**：同一个"改密码"动作，在两种场景下的安全语义相反。合成一个接口必有一边是错的：要么本人改密码把 Key 全废（体验灾难），要么管理员能重置后登录读 Key（隔离失效）。

**判定依据**：操作者是否等于目标用户，**不是角色**。superadmin 改自己的密码也走保留路径。

**违反后果**：合并接口 = 给部署者一条读取任意 Key 的合法通道，D003 直接作废。

## D005 DEK 只驻内存，重启后需重新解锁

**日期**：2026-10-23
**决策**：DEK 存在进程内内存 Map，不落盘、不进 Redis、不进日志。服务重启后 DEK 丢失，用户需进后台点一次"解锁"（输入密码）。

**理由**：这是 D003 的必然推论。任何让 DEK 在无用户参与时可得的持久化方案，都会同时让部署者可得。

**已接受的代价**：用户确认"服务器不会无故重启，重启解锁可以接受"。

**配套要求**：未解锁时机器人不能静默失败——发预设话术并通知 owner 解锁。

**违反后果**：为了让机器人"重启后自动恢复"而把 DEK 持久化，等于放弃整个隔离模型。

## D009 审计日志只增不改

**日期**：2026-10-23
**决策**：`AuditLog` 在应用层不注册任何 UPDATE / DELETE；记录带 `prevHash` + `hash` 构成哈希链；提供完整性校验接口。

**理由**：如果审计可以被删改，那么"管理员没动过你的 Key"这句话无法证明。哈希链让任何中间记录的删改都会导致后续校验失败——包括在数据库层面直接动手。

**违反后果**：审计沦为摆设，事件发生后无法自证清白。

## D011 `mind` 是可选装饰器

**日期**：2026-10-23
**决策**：拟人表现层（状态机、发言决策、双阶段生成、表达层）每一层都可独立关闭。全部关闭后，系统仍能完成"进消息 → 调模型 → 回消息"的最小闭环。

**理由**：D002 的推论。拟人的价值在于叠加，但基础链路不能被它绑架。调试模型问题时需要能一键关掉所有装饰。

## D012 多平台扩展：platform / protocol / capabilities 三者分离

**日期**：2026-10-23
**决策**：

- `Platform`（哪个平台：qq / douyin / bilibili）与 `AdapterProtocol`（用哪种协议接入：onebot / official / douyin-open / bili-open）是两个独立概念。同一个平台可能有多种接入实现（QQ 既有 onebot 也有 official，能力不同）。
- `IAdapter` 必须声明 `capabilities: PlatformCapabilities`。**上层读能力声明做决策，禁止判断 platform 字符串。**
- `InboundMessage` 携带 `platform` 字段，`SessionKey.kind` 从 2 种扩展为 5 种：`private` / `group` / `comment` / `danmaku` / `live`。
- 「对话消息」与「平台事件」在契约层分离：`InboundMessage` 走对话管道，`PlatformEvent`（进场 / 礼物 / 关注 / 上舰）走反应策略。

**理由**：
抖音、B站与 QQ 的差异不是协议差异，是**社交模型差异**：

| 差异 | QQ 群 | 抖音评论 | B站弹幕 |
|---|---|---|---|
| 回复可见范围 | 群内 | **全网公开** | 视频下公开 |
| 能否主动发起 | 能 | 需用户先私信（48h 窗口） | 不能 |
| 单条字数 | 4500 | 1000 | 200 |
| 风控形态 | 账号封禁 | 内容下架 + 限流 | 混合 |
| 消息之外的事件 | 少 | 礼物、进场 | 上舰、SC |

如果不在契约层抽象，加平台时 `persona` / `rules` / `pipeline` / 前端会同时长出 `if (platform === 'qq')`，改造成本从 3 个文件扩散到十几个模块。

**明确不做的**（避免过度设计）：
- 现在不实现抖音 / B站适配器（YAGNI）
- 不建 PlatformRegistry、插件化动态加载机制
- 不做跨平台账号绑定与统一身份

**违反后果**：业务代码里出现平台字符串判断，新增平台从"写一个 adapter"退化成"全项目搜索替换"。

## D013 平台适配器以独立包存在，不与主服务混合开发

**日期**：2026-10-23
**决策**：

- 主服务（`src/`）只依赖 `@newjob/contracts` 与各 adapter 包。**适配器代码不允许放在 `src/` 下。**
- 每个平台一个独立包 `@newjob/adapter-{platform}`，自带 `manifest`（能力声明 + 配置字段 + 指标）。
- 前端根据 `manifest.configFields` **动态渲染配置表单**，不为新平台改前端代码。
- 适配器包禁止：依赖 `@newjob/core`、访问数据库、自己实现重试/限流/记账（那些是主服务职责）。

**理由**：
- 需求是"抖音/B站作为新的子项目开发，不混合"。
- 边界划在**目录**上只是代码整洁；划在**包**上才有依赖方向约束——适配器在物理上无法反向依赖主服务，独立开发才成立。
- manifest 驱动前端，让"接入管理系统"变成"加一行依赖"，而不是改 N 个页面。

**当前结构**：

```
packages/contracts     @newjob/contracts   主服务与所有适配器的唯一共享依赖
packages/adapter-qq    @newjob/adapter-qq  QQ 适配器（骨架）
src/                   主服务（编排、人设、模型、记忆、合规）
```

**明确不做的**：
- 不做运行时插件热加载（不扫描 node_modules 自动发现，显式注册即可）
- 不做跨进程 RPC（预留边界，不实现）
- 不做适配器 API 版本化兼容（自用，版本对齐即可）

**违反后果**：适配器里出现 `import ... from '../../src/...'`，包隔离形同虚设，独立开发退化成"在同一个仓库里分目录写"。

## D014 KDF 库固定 `@node-rs/argon2`，不换 `argon2` 包

**日期**：2026-10-23
**决策**：Argon2id 派生只用 `@node-rs/argon2`（napi 预编译二进制）。不引入 `argon2`（`node-gyp-build`）包，**也不允许两个 KDF 库并存**。

**理由**：

- 2026-10-23 在开发机（Windows / Node 22）实测过两个库，**`argon2` 是能用的**：0.45.1 自带 `prebuilds/win32-x64`，14 秒装完，Argon2id m=64MiB/t=3/p=4 出 32B 正常（约 30ms）。所以这条决策的依据**不是"前者跑不起来"**。
- 真正的区别在失败路径：`argon2` 用 `node-gyp-build` 探测预编译包，平台/ABI 对不上时会**回落 node-gyp 现场编译**（需要 VS Build Tools + Python）；`@node-rs/argon2` 是 napi 二进制，没有这条回退路径。
- 本项目是自用、单机、长期跑在 Windows 上的东西。"某台机器装不上依赖"这种排查成本，远高于两个库之间那点性能差异。
- 切换成本很低（只有 `src/common/crypto/argon2.ts` 与一条 `parseOptions` 反查用例受影响）。**正因为低，才更需要一条决策钉住**——否则每次重构都会被"顺手换个库"。

**明确不做的**：

- 同时保留两个 KDF 实现（`SECURITY.md` 第 8 条第 12 条：不允许存在两种解密路径，同一精神适用于派生）
- 为"兼容"写一层 KDF 库适配接口（YAGNI，只会让参数更难被检查）
- 更换 KDF 算法本身（bcrypt / scrypt 一律否决：与 `SECURITY.md` 第 2 节的参数表不符，且更换库就等于换派生结果，全部 `wrappedDek` 失效）

**代价**：`@node-rs/argon2` 的 `Algorithm` / `Version` 是 `declare const enum`，运行时是空对象，必须写成数值常量并加断言锁住（见 `CONVENTIONS.md`）。这是已知成本，已用测试覆盖。

**违反后果**：改用 `argon2` 后一旦在某台机器/CI 上触发编译回退，会出现"只有我这台能跑"的孤立故障；更糟的是有人为了绕开安装问题去动 KDF 参数或算法——那会让所有 `wrappedDek` 永久解不开，用户全部 Key 报废。

## D020 人格双层（种子 + 演化），记忆与人格归属 Agent

> **⚠️ 2026-10-24 已被 D023 修订**：**归属主体改回 `BotInstance`（单个社交平台账号）**。
> 原因：本项目只保证"单个社交平台内"的演化，跨社交平台不共享人格与记忆（另立项目）。
> D020 的**四层结构、演化闸门、prompt 组装顺序、上下文分层**全部保留，只有"挂在哪"这一段作废。
> 下文「1. 新增 Agent 层」与归属表视为历史记录，实现以 D023 为准。

**日期**：2026-10-24
**决策**：

**1. 新增 `Agent` 层**（用户的 AI 身份）。归属判定只有一句话：
> **"这是谁的经历"看 Agent，"从哪个口进来的"看 Instance。**

| 挂 `agentId` | 挂 `instanceId` |
|---|---|
| `Persona`（人设） | `BotInstance`（平台账号） |
| `MemoryItem`（记忆） | `Session`（某个群/某个人的会话） |
| `Relationship`（关系、亲密度） | `InstanceEvent`（连接/发送事件） |
| `AgentState`（mood / energy） | `ModelUsage` 保留实例维度（同时加可空 `agentId` 便于按 AI 汇总） |

- `MemoryItem.instanceId` 降级为**来源渠道**（可空），不再承担归属；
- `Relationship` 唯一键改为 `[agentId, platform, peerId]`：同一个人在不同社交平台是两条记录，暂不合并（D012）。

**2. 人格分四层**：

| 层 | 载体 | 谁能改 |
|---|---|---|
| 不可演化 | 独立红线字段/表 | 谁都改不了（含 superadmin） |
| 种子 | `Persona`（`version` + `archivedAt`，只读） | owner 编辑（产生新版本） |
| **演化** | `SelfState`：traits 数值 + 第一人称自述 + 形成的看法 | **只有反思任务**，且必须过代码闸门 |
| 瞬态 | `AgentState`：mood / energy | 每轮对话 + 定时衰减 |

**3. 红线结构不可达**：红线不进 `SelfState`，反思的输入与输出 schema 里都没有它。
靠"没有代码路径"，不靠提示词里写"请勿修改"。出口再过一次规则/合规检查（M6）作为第二道。

**4. prompt 顺序固定**：红线 → 出生设定 → 现在的你 → 关系 → 情境 → 语气提示。
种子用"你出生时…"叙述，**不用命令句**——写成"你必须…"模型只会背台词，写成"你出生时…"它才会延续。

**5. 演化闸门**（写死在代码，不开放配置放宽）：

- 单次维度变化 |Δ| ≤ 0.03，单日累计 ≤ 0.08（人不会一夜变一个人）
- clamp 到 `[0.05, 0.95]`；`edge`（棱角）下限 0.25，防漂成讨好型
- 反思输出必须引用真实 `memoryIds`，否则整次丢弃（防编造经历）
- 输出若试图修改红线/规则 → 整次丢弃 + 审计 `self.evolution_rejected`
- 写入前先落版本快照，支持回滚到任意版本

**6. 人格必须落库，不寄生在上下文窗口**。上下文用分层压缩：
工作记忆（最近 N 轮原文）→ 情节摘要（每 30 轮/每天）→ 语义记忆（关于人的稳定事实）
→ 自我叙事（`SelfState.narrative`，≤600 token，超 8 段压缩）。原文留在 `Message` 表可检索，只是不进 prompt。

**理由**：

- 用户会在 QQ / 抖音 / B站 各有一个号，但背后是同一个 AI、同一段人生。记忆挂实例 = 换号就重生，这正是要避免的。
- 用户要的是"性格自己长"，人格卡只给出身；卡片当约束用会把它变成复读机。
- `SelfState` 落库 + 上下文分层，保证重启或爆窗口只是"聊得顺不顺"，不是"它是谁"。

**明确不做**：

- 不做 agent runtime / 工具循环 / 向量库（D002）
- 不做跨平台身份合并（D012，但结构留门：`platform` + `peerId` 分离）
- 不做无限上下文（分层压缩 + 原文留库检索）

**违反后果**：

- 记忆挂实例 → 换平台号就"失忆重开"；
- 红线写进人格卡 → 演化必然越过（模型会把"设定"当可协商文本）；
- 反思直接写库不设闸门 → 编造经历、性格跳变、出事无法回溯；
- 人格只存在上下文里 → 重启或压缩即人格消失，这是最贵的一次返工。

## D021 Agent 与模型解耦：Provider 可切换，人格资产不随之改变

**日期**：2026-10-24
**决策**：`Agent` 只持有**模型路由策略**（`modelMain` / `modelCheap` / `modelFallback` + `credentialId`），不绑定任何厂商。
切换 Provider（DeepSeek / OpenAI / Claude / 通义…）只改配置；`Credential` 仍挂 `User`，多把 Key 组成池供降级链使用。
`BotInstance` 上的模型字段降级为**实例级覆盖**（为空则用 Agent 的），对应 D007 五级覆盖里的第三级。

**理由**：

- 用户无法预先确定用哪家（DeepSeek / Codex / 其他），必须能随时换；
- 模型是执行器，人格与记忆是资产，资产不该因为换执行器而迁移；
- 把 provider 渗进业务代码后，`if (provider === 'deepseek')` 会扩散到 prompt 与记账逻辑。

**代价与处理**：换模型语气会漂移。处理方式是"人工观察 5~8 轮 + 需要时补 few-shot 校准"，
**不做自动人格改写**——自动改写会让"换模型"悄悄变成"换人"。

**跨模型平台继承（本条的硬要求）**：人格与记忆表里**不允许出现 `provider` / `credentialId` / `model` 任何字段**。
换 Provider 或换 Key 只改 `BotInstance.credentialId` 与 `modelMain`，人格、记忆、关系零迁移零丢失。
反例：把 provider 写进 `Persona` / `SelfState` / `MemoryItem`；"换模型时重置人格"。

**明确不做**：不为每家厂商写适配器（D006：3 个协议 + preset 表）。

**违反后果**：换模型从"改一行配置"退化成"全项目搜索替换"，且很容易顺手把人格数据也改掉。

## D022 人格重置分四档，版本化可撤销

**日期**：2026-10-24
**状态**：规则已定稿，实现留到 M4（管理页）+ M5（演化真正跑起来）

**决策**：不做单一"重置"按钮，分四档，用户必须选范围：

| 档 | 动作 | 场景 |
|---|---|---|
| ① 回退 | `SelfState` 回到指定版本，记忆不动 | "它最近变得太油了" |
| ② 性格重置（默认） | `SelfState` 清空 → 用当前种子重建；**记忆与关系保留** | "性格重来，但还认得我" |
| ③ 重新出生 | 新种子 v2 + 清 `SelfState` + 清 episodic + 关系归零；**semantic 记忆默认保留，显式勾选才清** | "换个人来陪我" |
| ④ 换 Agent | 新建 Agent，旧的归档只读，实例重新绑定 | "我想养两个" |

共同约束：

- **重置是版本操作，不是 DELETE**。旧种子、旧 `SelfState`、旧叙事全部归档，必须能撤销；
- **`semantic` 记忆默认保留**。清了它等于"不认识你"，与"性格变了"是两件不同的事，不能捆在一个按钮里；
- 重置后必须跑一次初始化，生成第一版自述。否则"现在的你"为空，模型会退回死守种子卡；
- **红线不在任何重置范围内**（它不属于 Agent）。

**理由**：误点一次清掉几个月记忆是不可接受的失败模式；而"想改性格"和"想让它忘了我"是完全不同的诉求。

**违反后果**：合并成一个重置 → 只想改性格却把关系清了；用 DELETE 实现 → 误操作不可恢复。

## D023 人格与记忆的作用域是「单个社交平台账号」

**日期**：2026-10-24
**决策**：

**1. 作用域 = `BotInstance`（一个社交平台账号一段人格）。**
同一用户在 QQ、抖音、B站 各有账号时，是**三份互不相干的人格与记忆**：
每个平台账号自己生成初始人格、自己演化、自己积累关系。

**2. 跨社交平台明确不合并。**
不做身份合并、不做记忆迁移、不做人格继承。换平台 = 重新生成初始人格、从零开始演化。
"跨平台演化/继承"属于**另一个项目**，本仓库不实现、不预留运行时代码
（唯一保留的接口是中性的：`BotInstance.platform` / `accountId` 已经把平台与账号做成了数据）。

**3. 跨模型平台（Provider）继承是必须的。**
人格与记忆表**不允许出现 `provider` / `credentialId` / `model` 任何字段**。
换 DeepSeek → OpenAI → Claude，只改 `BotInstance.credentialId` 与 `modelMain`，
人设、记忆、关系、亲密度**零迁移、零丢失**——因为它们本来就不认识"哪个模型在说话"。

**4. 账号与人设严格 1:1**：一个社交账号只有**一条人格线**（`Persona` 的多个 version 是同一人格的迭代，不是多个人格）。
用户想在同一个社交账号下"换人格"，触发的是**该账号的 AI 重置**（D022 档③：新种子 + 清演化 + 清情节记忆），
**不允许两套人格在同一账号下并存运行**——并存会立刻出现"同一句话两个人格抢着答"。

**5. 归属判定**：
> **"这是谁的经历"= 这个社交平台账号（`instanceId`）；"谁在说话"= Provider（可随时换，不落人格）。**

**理由**：

- 本项目定位是**聊天接入 + 单平台内的拟人演化**，不是 agent 成长平台。跨平台统一身份是另一个量级的问题（身份判定、隐私串台、合并粒度），放进这个仓库会把边界撑破。
- 但"换模型就失忆"是不可接受的：Provider 是执行器，人格是资产。资产挂在账号上，天然与执行器解耦。
- 这两个方向容易混：**跨社交平台 = 不继承**；**跨模型平台 = 必须继承**。写混一条就会做出"换号重新养"或"换模型就清空"的灾难。

**明确不做**：

- 不做 `Agent` 中间层（2026-10-24 曾按"跨平台共享"设计过一版并合并，同日按本条回退）
- 不在 `Persona` / `MemoryItem` / `Relationship` / `AgentState` 上加任何 provider 维度
- 不做跨平台账号绑定表（留给下一个项目）

**违反后果**：

- 把人格挂到"用户级"或"跨平台级" → 抖音上的聊天内容会跑到 QQ 提起来，当场穿帮，且用户无法解释；
- 把 provider 写进人格表 → 换模型等于换人，用户几个月的相处归零；
- 为了"将来可能共享"先加中间层 → 多一层 join 与一个没人用的概念，接手的人每次都要想"这层到底干嘛的"。

**验收方式**（M2 落地时）：切换 `BotInstance.credentialId` / `modelMain` 后，
`Persona` / `SelfState` / `MemoryItem` 三张表的行数与内容必须完全不变；补一条集成测试锁住。

## D024 预算挂在人格（社交账号）上，不挂 Key

**日期**：2026-10-24
**决策**：

**1. 预算字段落 `BotInstance`**（= 一个社交账号 = 一份人格）：

| 字段 | 含义 |
|---|---|
| `dailyBudgetCents` | 日预算，单位"分"，`0` = 不限 |
| `monthlyBudgetCents` | 月预算，`0` = 不限 |
| `budgetPolicy` | 超限策略：`downgrade`（切 `modelCheap` 继续聊）/ `block`（不回复 + 通知 owner） |

**2. `Credential` 上不再有预算字段**（同日删除，避免两个来源）。
凭据只负责"用哪把 Key、优先级、健康状态"。

**3. 计费口径**：
`ModelUsage` 每次调用一行（`instanceId` / `credentialId` / `provider` / `model` / `purpose` / token / `costCents`）；
单价取**当次使用的 credential 的 `catalogJson`**，没填则回落 Provider 预设价并记一条 warn。
聚合维度随查询而定：按人格看 `instanceId`，按厂商看 `provider + model`，按 Key 看 `credentialId`。

**4. 80% 时无论策略都先告警**；`block` 时机器人不静默失败，要给 owner 推一条通知（M6）。

**理由**：

- 预算挂 Key 的话，换一把 Key 额度就清零，等于没有预算——而"换 Key"在自用场景里很常见（Key 过期、换渠道、换厂商）。
- "这个人格每月能花多少"本来就是人格的属性（愿不愿意为它花钱），不是凭据的属性。
- 一个用户可能同时挂多个社交账号，每个账号的预算要能分别设，这只有挂在实例上才表达得出来。

**明确不做**：

- 不做"跨人格共享预算"（那是用户级配额，属于以后的多租户计费）
- 不在 `Credential` 上加任何预算字段（两处会有两个真相）
- 不做"换 Key 重置预算"

**违反后果**：预算挂 Key → 用户频繁换 Key 时账单失控；单价用全局常量 → 第三方渠道价与官价不同，账单系统性偏差。

## D025 余额三态 + 熔断只暂停路由 + 兜底按故障时长分级

**日期**：2026-10-24
**决策**：

**1. 余额是三态，不是"有/没有"**（`Credential.balance*`）：

| 状态 | 含义 | UI |
|---|---|---|
| `api` | 厂商提供余额接口（DeepSeek `/user/balance` 已核实） | 显示金额 + 查询时间 |
| `inferred` | 只能靠错误码事后确认（OpenAI / Anthropic / Gemini） | 「未知 · 该厂商不支持查询」+ 充值链接 |
| `unverified` / `unsupported` | 未实测 / 不提供 | 同上 |
| `na` | 本地模型（Ollama） | 「不适用」 |

余额接口声明写在 `providers/presets.ts`（纯数据），**代码里不许出现 `if (provider === 'deepseek')`**。
**绝对不估算**：查不到就显示未知，编一个数字比不显示更糟。

**2. 熔断只改"健康层"，不动配置**：

| 层 | 字段 | 谁能改 |
|---|---|---|
| 配置 | `apiKeyEnc` / `label` / `priority` / `enabled` | 只有用户 |
| 健康 | `cooldownUntil` / `unavailableReason` / `lastCheckOk` / `lastError` | 系统自动写，可自愈 |
| 用户禁用 | `enabled=false` + `disabledBy='owner'` | 只有用户 |

路由条件 `enabled=true AND (cooldownUntil IS NULL OR cooldownUntil < now)`；冷却到期 half-open 单次试探；
恢复三条路径（巡检发现恢复 / 手动重测 / 试探成功）。
**禁止**：删凭据、清密文、改 `enabled`、把 `balance` 报成 `auth`。

**3. 兜底按"故障预期时长"分级**，不是所有失败都回同一句话术：

- 分钟级（网络 / 5xx）：话术一次（同会话 1 小时 1 次、全天 3 次），之后静默
- 小时~天级（`balance` / `auth`）：**静默**（群聊尤其），立即精确通知 owner
- 我方 `block`：话术一次

理由：短时说"有点事"是拟人，长时说就是骗人；持续敷衍比不说话更伤关系。

**4. 通知去重**：同一 `(instanceId, unavailableReason)` 30 分钟内一条，带"已静默 N 次"。

**理由**：

- 用户遇到"机器人不说话"时，第一反应是"你们平台坏了"。后台必须能立刻回答"是厂商余额没了 / Key 失效了 / 你设的限额到了"。
- 余额查不到不代表发现不了欠费——错误码能事后确认，只是失去预警窗口。所以两条腿都要有。
- 查余额需要明文 Key，而明文只在解锁后存在（D005），因此**未解锁时只能显示缓存快照**，这是设计代价不是 bug。

**明确不做**：

- 不估算余额、不把"未知"显示成 0
- 不因欠费删除/禁用用户的 Key（用户在后台配的东西不能自己消失）
- 不对终端用户说"余额不足"（那是 owner 的运维信息），只走话术或静默
- 不在每次推理前查余额（白加延迟），定时巡检 + 被动识别足够

**违反后果**：

- 熔断时删 Key → 用户充值后还要重新配置一遍，这是最招人恨的体验；
- 所有失败统一回话术 → owner 分不清是欠费、Key 失效还是我们的 bug，排查成本全转嫁给用户；
- 余额编造或显示 0 → 用户拿错误数字做决策。

## D026 故障兜底话术由用户配置，且必须是预存文本

**日期**：2026-10-24
**决策**：

**1. 话术存 `Persona.fallbacksJson`**，按 `[槽位][渠道]` 两级：

```jsonc
{
  "shortOutage": { "private": "我这会儿有点事，等下找你", "group": null },
  "longOutage":  { "private": null, "group": null },
  "budgetLimit": { "private": "今天有点累了，明天再聊", "group": null }
}
```

| 槽位 | 触发情形 | 默认 |
|---|---|---|
| `shortOutage` | 网络抖动 / 5xx / 超时（分钟级，会自愈） | 私聊一句话，群聊不说 |
| `longOutage` | 余额耗尽 / Key 失效（小时~天级） | **全部不说**（与 D025 的分级一致） |
| `budgetLimit` | 我方日/月限额用尽 | 私聊一句话，群聊不说 |

**2. `null` 表示"不说"，空字符串一律非法。**
空串在实现里会被当成"发一条空消息"，比不发更诡异，还可能触发平台报错。校验里直接把空串拒掉，并提示改用 `null`。

**3. 必须是预存文本，**不允许**在故障时调模型生成。**
故障场景里模型恰好不可用，让它"现编一句"会形成死循环（调用失败 → 生成兜底 → 又调模型 → 又失败）。
兜底路径必须零依赖、零延迟、零 token。

**4. 群聊默认全部不说。**
群里被 @ 多次换来一句"等下找你"，观感比安静更差，而且容易被当成刷屏。

**5. 校验规则（写死在 `persona/fallbacks.ts`）**：

- ≤ 60 字（再长在群里会被拆条，失去"一句话带过"的效果）
- 禁止链接（防被当广告 / 钓鱼）
- 禁止运维字眼（`余额` / `欠费` / `充值` / `限流` / `接口` / `额度` / `API` / `Key` / `token`）
- 占位符只允许 `{nickname}` / `{groupName}`；其它 `{xxx}` 直接报错，避免用户以为支持模板引擎
- 频率上限**不由文案控制**：1 小时 1 次、全天 3 次在表达层强制执行，否则用户可以写长句刷屏

**6. 两套文本，不能合用**：

| 受众 | 内容 | 特征 |
|---|---|---|
| 对端（聊天里的人） | 用户配的话术 | 拟人、模糊、"不说"合法 |
| owner（后台通知） | 系统生成 | 精确：哪个实例、什么原因、怎么办、充值链接 |

让 owner 也只看到"我这会儿有点事"，就等于把 D025 解决的问题又还回去了。

**理由**：话术是人格的一部分。写死一句客气的"系统繁忙"，一个说话带刺的人格立刻变得不像它——
而用户配的话术可以保持语气一致，且"不说"本身也是一种人格表达（高冷的人不解释）。

**明确不做**：不做模板引擎（只有两个占位符）、不做多语言、不允许用户配置"向对端解释故障原因"。

**违反后果**：

- 让模型生成 → 故障时死循环，最坏情况是机器人彻底不回；
- 空串当"不说" → 发空消息或被平台拒绝；
- 话术里出现运维词 → 对端困惑或恐慌（"什么余额？是不是骗我"）；
- 群聊默认说话 → 刷屏。

## 依赖类取舍写在哪

D014 是个示范。**满足以下任一条件的依赖选择，必须写成决策，不能只写在 `STATUS.md` 的注记里**：

1. 影响安全等级（KDF、加密算法、随机源、TLS、鉴权库）
2. 含原生模块（原生编译/ABI/平台差异会变成"装不上"）
3. 决定不可逆的数据格式（密文格式、哈希格式、序列化格式）
4. 有明确被否决的替代方案（否则下次会有人重新提一遍）

理由是 `STATUS.md` 是**会被反复重写的进度文档**——第 2 步那段就被重写过一次，原来的依赖注记当场丢失。决策文档只追加、不重写，才是这类约束该待的地方。

## D015 凭据删除走物理删除，是「软删除优先」的明确例外

**日期**：2026-10-24
**决策**：`DELETE /api/credentials/:id` **真删行**（`deleteMany`，`where` 带 `ownerUserId`），不改成 `enabled = false`。
`CONVENTIONS.md` 里「软删除优先（凭据、实例、人设）」这一条，凭据在此被明确排除。

**理由**：

- **留着的密文是纯负债。** 软删除只是把一行藏起来，`apiKeyEnc` 仍然躺在库里和所有历史备份里。用户点"删除"的语义应该是"这把 Key 不在了"，而不是"我们看不见它了"。
- **恢复价值接近零。** 凭据删错了，去 provider 后台重新生成一把即可；它不像人设、实例那样承载长期积累的内容。为这种低价值恢复能力付出"永久保留密文"的代价，不划算。
- **schema 里没有 `deletedAt`**，做软删除要加列 + 迁移 + 所有列表查询补过滤，还要处理"已删除凭据是否计入配额"。收益远小于复杂度。
- **停用与删除是两件事，都要保留**：`enabled = false` 表示临时停用（保留密文，可恢复，`reset-password` 用的就是这条路）；`DELETE` 表示销毁。混成一个动作后，`reset-password` 的"停用全部"会变成"删掉全部"，那是另一个破坏性事故。

**可追溯性不靠数据库行**：删除会写 `credential.delete` 审计，`before` 里带 `provider / label / keyMasked`。审计哈希链保证这条记录改不动，"删过哪把"永远是清楚的。

**明确不做的**：

- 不做"回收站 / 30 天后清理"（多一张表、多一个定时任务，只为一个几乎不会用到的恢复场景）
- 不把删除实现成 `enabled=false` + `label` 打标（伪软删除，比真删更糟：既留了密文，又假装删了）

**违反后果**：改成软删除后，用户以为已经消失的 Key 仍可被解密（只要 DEK 在内存），且 `reset-password` 与用户删除两条路径会在同一批字段上打架，配额统计随之失真。

## D016 实例接入配置存数据库，连接由用户解锁触发

**日期**：2026-10-24
**决策**：
1. QQ 号、NapCat 的 WS 地址、Access Token **全部存 `BotInstance`**，不写进 `.env`、不写进代码常量；
2. 每个 QQ 号一条记录，换号 = 新建一条（或改 `accountId`）；换服务器 = 改 `endpoint`；
3. **实例连接必须先解锁**：token 用 owner 的 DEK 加密存储，`connect` 时才解密，因此进程重启后实例不会自动上线。

**理由**：

- 需求原文是"QQ 号要在管理页面自己输入切换"。只要号在环境变量里，换号就得改配置 + 重启，等于没有切换能力。
- 用户的实际路线是"先本机测，确认后迁云"。如果接入地址是环境变量，迁移就多一步"改服务器上的 `.env`"，而这一步错了排查成本很高（机器人不连、日志只说连接失败）。存库里则改一条记录即可。
- 接入参数属于**业务数据**（多实例、可增删、要审计），环境变量属于**进程密钥**（`SESSION_SECRET`、端口）。两者混在一处，早晚出现"为了改个端口把 token 也搬家"的事故。这与 D007（配置面/数据面分离）同一条思路。
- token 用 owner 的 DEK 加密，与 API Key 共用一套体系：**部署者拿到整库也解不开**。这条不是新设计，是把 D003 的边界延伸到接入凭据。

**代价（必须接受）**：进程重启后实例**不会自己上线**。要等用户登录/解锁后再点连接；没有一个"服务端主密钥自动解 token"的捷径。

**明确不做的**：

- 不在 `.env` 里放 `ONEBOT_WS_URL` 这类"默认值兜底"（`.env.example` 里那两行是 M1 之前的占位，实现后已不再读取，别把它当配置入口）
- 不做"服务端 KEK 再包一层 token"来自动恢复连接——这就是 D003 否决过的便利方案
- 不做"启动时自动连所有 `enabled` 实例"：没有 DEK，它只能连没有 token 的实例，行为不一致

**违反后果**：一旦引入服务端可解密的 token 存储，部署者就同时拿到了"所有用户的模型 Key"和"所有机器人的接入 token"，D003 的承诺当场作废；而把配置挪回环境变量，则会让"后台换号"这个需求根本无法满足。

## D017 协议端地址默认只允许本机/私网；登录态只在协议端

**日期**：2026-10-24
**决策**：三条一起，不能只做其中一条：

1. **接入地址准入**：`BotInstance.endpoint` 默认只接受回环（127/8、`localhost`、`::1`）、
   私网（10/8、172.16/12、192.168/16、169.254/16）、组网地址（100.64/10，Tailscale 用）、
   单标签主机名与 `.local/.internal` 域名；**其余一律 `REMOTE_ENDPOINT_BLOCKED`**，
   除非显式 `ALLOW_REMOTE_ADAPTER=true`（只认 `true`/`1`）。create / update / connect 三处都校验。
2. **连接后核验身份**：`get_login_info` 的 `user_id` 必须等于实例配置的 QQ 号，不等则断开；
   `get_status.online === false` 也断开；`good === false` 只告警。
3. **登录态不搬家**：NapCat/NTQQ 的数据目录不入 git（`.gitignore` + `pnpm check:local-data`）、
   不随迁移复制、换机时在新机器重新扫码生成。

**理由**：

- 我们的信封加密（D003）保护的是"用户上传的模型 Key"。**QQ 登录态从来不在这个边界内**，
  它在协议端的工作目录里。所以对它的保护只能是"不给外界接触的机会"，不能是"加密后随便传"。
- `endpoint` 是数据（D016），意味着用户**能**填任意地址。这不是能力，是缺口：
  指向别人的 NapCat = 把"读我所有消息 + 以我身份发消息"的权力交出去。
  这类事故不会报错，只会表现为"机器人怪怪的"，排查成本极高。所以默认拒绝。
- 允许 Tailscale 的 100.64/10 与 `.local` 是本项目明确推荐的跨机形态（家里跑 QQ、云上跑服务），
  堵掉它们等于逼用户去开公网端口，反而更不安全。
- 连接后必须核验身份：`selfId` 用来判断"有没有被 @"、过滤自身消息。号填错时现象是
  "接上了但不理人"，与"NapCat 挂了"难以区分。核验把这类错误变成一句明确的报错。
- 迁移时搬数据目录是**最容易被当成正常操作**的泄露路径：一个 zip、一次网盘同步、一次
  "拷到新电脑试试"。它复制的是账号控制权，而且事后无法收回。相比之下重新扫一次码只要一分钟。

**明确不做的**：

- 不做 QQ 密码托管、不做自动登录（等于把账号交给了服务器，且必然要处理验证码/设备锁）
- 不做"协议端数据加密后随迁移搬运"：加密了也要在新机器解密，仍然是一份可解开的控制权
- 不做"连接时弹窗确认公网地址"：确认弹窗点两次就变成肌肉记忆，等于没有
- 不把 `get_status.good === false` 当硬失败：它是"接收链路不健康"的自评，
  偶发抖动很常见，硬失败会导致频繁误断；只告警 + 保留人工判断

**违反后果**：跳过第 1 条，一个填错的地址就能把 QQ 号交给第三方；跳过第 2 条，
填错号会长期以"机器人不回复"的形式存在，风控数据全错；跳过第 3 条，
一次"顺手拷贝"就把登录态扩散到网盘、聊天记录、另一台电脑上，且 git 历史删不干净。

## D018 接入方向默认反向（NapCat 连我们），token 由本服务在握手阶段校验

**日期**：2026-10-24
**决策**：`BotInstance.adapterMode` 默认 `server`。适配器把"谁发起 TCP 连接"和"协议怎么跑"
拆成两层：`OneBotTransport`（client / server 两种实现）+ 共享的 `routeIncoming` 收发逻辑。

- `server`：本服务监听（默认 `ws://127.0.0.1:3002`），NapCat 用「反向 WebSocket」连进来；
  握手阶段由 `verifyClient` 比对 token，不匹配直接 401，连接不会建立。
- `client`：本服务拨号到 NapCat（旧的 `ws://127.0.0.1:3001`），保留但不再是默认。
- 反向模式下 `accessToken` **必填**（少于 8 位直接拒绝启动）：这一端是我们自己开的端口，
  空 token 等于对任何能连上本机的进程开放。
- 地址护栏按用途给不同文案：`server` 拒绝在公网地址上**监听**，`client` 拒绝**连接**公网地址。

**理由**：

- **上游鉴权是坏的，且修不了。** NapCat 4.18.41 的 `websocketServers` 把 HTTP 中间件签名
  `authorize(token, req, res, next)` 用在 WS 上只传 3 个参数，`next` 未定义 → 三个分支
  （空 token / 匹配 / 不匹配）**都是"连上了"**，异常还被 async 回调吞掉。真机实测确认。
  继续用正向模式，token 就只是个装饰，安全性全靠"端口只绑 127.0.0.1"。
- **鉴权要放在我们能控制的一侧。** 反向模式下 token 校验在我们进程里，是握手阶段的前置条件，
  不依赖任何上游实现、也不存在"连上之后再判断"的窗口。
- **顺带解决迁云。** 反向是 NapCat 往外连，云服务器不需要开放任何入站端口，
  也不用内网穿透/隧道；这比"云上开 3001 等服务连"收敛一整个数量级。
- **断线语义更简单。** 正向要靠退避重连；反向只要监听还在，NapCat 自己的 `reconnectInterval`
  会一直重试，我们不需要重连状态机（`online` / `connecting` / `offline` 三态即可）。
- **真机验证过**：错 token 握手得到 HTTP 401，NapCat 带正确 token 连入后 `online`，
  `get_login_info` 核验通过。测试里也钉住了这两条（`onebot-ws-server.test.ts`）。

**明确不做的**：

- 不降级 NapCat：QQ 9.9.33 与旧版 NapCat 的兼容性不确定，降级换来的确定性不如换方向。
- 不自己实现 WS token 的"连上后校验"：那正是上游那个 bug 的形态，握手拒才是干净的。
- 不在反向模式下允许"无 token 只靠 127.0.0.1"：端口绑定是部署细节，会被一次 `0.0.0.0` 改掉。
- 不做两条通道同时在线：同一实例只认最后一条连接，旧连接立刻让位，否则同一条消息处理两次。

**违反后果**：默认值改回 `client`，token 鉴权立刻退化成装饰品（且没人会察觉，因为不报错）；
反向模式放开空 token，等于把机器人的控制权交给任何能连上该端口的本地进程；
反向模式下监听 `0.0.0.0`，等于把 OneBot 端口暴露到公网。

## D019 反向实例存 token 摘要，启动时自监听（不依赖 DEK）

**日期**：2026-10-24
**决策**：`BotInstance` 增加 `accessTokenDigest`（HMAC-SHA256(token, pepper)，hex）。
反向模式的握手校验只比摘要；`accessTokenEnc` 继续保留，供正向模式拨号和"重新填写"使用。

- **适配器只负责"怎么比"**：`AdapterDeps.verifyPeerToken?: (provided) => boolean` 由主服务注入，
  适配器不读环境变量、不碰密钥（D013 的边界不变）。
- **没有校验手段就不许监听**：`OneBotWsServer` 构造函数要求 `verifyToken` 必填；
  反向实例若既无明文又无摘要，`connect` 直接报错，不出现"监听了但不设防"的窗口。
- **老数据**（加列之前建的实例）启动时被跳过，不静默放开；用户下次手动连接时
  用 DEK 解密一次、顺手把摘要补上（`resolveCredentials` 里的一次性回填）。
- **启动自监听**由 `InstanceBootstrapService.onApplicationBootstrap` 触发，
  fire-and-forget，失败只告警不阻断启动。

**理由**：

- 这是"云端能常驻"的前提。反向模式下是我们监听、NapCat 连进来，而 `connect()` 需要 DEK
  才能解 token；DEK 又只在用户登录后存在内存（D005）。结果就是服务每次重启都要有人登录点一次，
  云端等于必须有人值守。
- 握手本来就是**比对**，不是解密：只要回答"这个 token 对不对"，摘要足够。
  把"能解密"和"能校验"分开，就解开了这个死结。
- 用 HMAC 而不是裸 SHA-256：token 是人填的，可能弱；加一个只有服务端知道的 pepper
  就不会被彩虹表反查。不用 argon2：这段在 `verifyClient` 里、每个连接一次，
  **同步且快**是硬要求，且 token 通常是 32 位随机串。
- 摘要泄库无意义（单向），比"为了能自启动而把明文放明文列"安全得多。

**代价（必须知道）**：换 `SESSION_SECRET` 会让所有摘要失效 → 需要在后台把 token 重新保存一次。
这条要写进运维说明，否则表现为"实例突然起不来且报 token 不匹配"。

**明确不做的**：

- 不把明文 token 存进明文列（那等于放弃信封加密的意义）
- 不让适配器自己去算摘要（它不该读 env、不该知道 pepper）
- 不在"没有摘要"时降级成"不校验也监听"（宁可不起）
- 不 await 启动自监听（反向 `connect()` 会等对端，几个实例就能把启动拖几十秒）

**违反后果**：为图省事把摘要改成明文，等于给零知识设计开一个后门；
去掉"必须等待对端"的失败分支，会留下"端口开着但没人校验"的窗口；
忽略 SESSION_SECRET 轮换的影响，会在某次重启后集体掉线且原因难以定位。
